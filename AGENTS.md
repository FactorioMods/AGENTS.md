## Working agreements
- User permits delegated checks; internal agents use `gpt-6.1-sol` with `low` reasoning effort (Light), unless the user changes this preference.
- Delegated agents may use all available task-relevant skills. Read the selected `SKILL.md` before applying it: code review for implementation/release review, performance optimization for measured bottlenecks, image generation for requested raster artwork, and computer use for required browser operations. Use Context7 only for a specific documentation gap. Share exact source/artifact identities and file ownership; do not add agents beyond the user's concurrency limit.
- Coordinate through [the agent workbench](knowledge/agent-setup.md) and [a bounded task brief](templates/agent-task.md). Delegate independent outcomes to peers with the same quality bar; keep dependent steps with their owner. Use private per-task workspaces, explicit source/resource claims, one canonical-result owner and identity-bound proof reuse. A completed agent needs a follow-up task to restart; a message alone does not restart it. Locks are cooperative bookkeeping, not authorization or a security boundary.
- Fetch authentic upstream history with `--no-tags` and compare matching releases before updating a fork. Preserve original upstream commits and authors, including their own merges. Rebase our changes onto that history as a linear series with one logical final fix or feature per commit; do not add fork merge commits. Preserve monorepo history with an explicit extraction commit; record unavailable sources instead of inventing ancestry.
- In mod repositories, retain final implementation commits only, one distinct fix or feature per commit. Fold its documentation, settings descriptions, changelog and version metadata into the owning implementation; do not retain standalone documentation, naming, formatting or release-policy commits.
- Keep one consolidated current stable changelog entry. Documentation cleanup alone does not justify a new version or changelog entry; preserve automatic-update ordering.
- Inspect upstream tag refs read-only when needed. Push only explicitly reviewed current tags; never use `git push --tags` or mirror original tags back into our forks after cleanup. Original repositories and private backup bundles retain their old refs.
- Before a public Git push, check every HEAD-reachable object with `GIT_NO_LAZY_FETCH=1 git rev-list --objects --missing=print HEAD` and run full `git fsck`. A non-shallow checkout can still be a partial clone with missing historical objects. Repair only through the pinned authentic upstream and verify HEAD, tree, index, refs, configuration and release artifacts remain unchanged. Reconcile uncertain writes through readback before considering another write.
- Preserve existing entity/item/recipe names, saves, recipes and balance unless the current task asks to change them.
- Test Factorio in a dedicated write-data directory with a separate mod directory and copied save. Never test against the player's live save or stop their game. Use CLI and `game.take_screenshot`, not GUI automation for Factorio.
- Inspect the installed Factorio API and vanilla prototypes. Online `latest` documentation may target a newer engine.
- Validate numeric settings through native inherited and derived prototype getters as well as parsed data-stage fields. Apply destination-specific bounds, preserve unrelated bonuses and value types, and compare the full evaluated prototype graph for disabled and default settings. Use actual supported settings before adding a compatibility correction.
- Validate visuals in game: all five tiers, adjacent placement, Alt icons, modules, fluids, inserters, loaders, day/night, active/low-load/idle. Studio renders alone are insufficient.
- Prefer native animation playback. Do not add per-tick Lua just to animate sprites.
- Keep mechanical objects rigid: real pivots, connected joints, limited piston strokes, stationary cables and no duplicate moving parts in the background.
- Keep raw saves, logs, credentials, player data and private build/test scripts out of public mod releases. Publish only reviewed reference assets and sanitized knowledge here.
- Confirm the physical checkout/worktree, branch, HEAD and existing edits before acting. Read the applicable `AGENTS.md` chain and preserve unrelated work. Old checkpoints grant no new authorization.
- While the user plays, run headless checks in isolated profiles with copied saves. Never change their running game, saves, network or Steam settings. A benchmark's virtual connected player does not prove multiplayer compatibility.
- The current all-save migration requires no physical game windows. Native headless servers and full Linux clients inside a private offscreen Xvfb display are suitable; a hidden Windows client can still create a physical window. Offscreen real-peer tests must prove native join, synchronized play, host save/reload and rejoin. Keep the display, runtime, mod directory, XDG files and saves isolated; do not alter HOME or Steam/network settings. Software-rendered timings do not measure the player's GPU performance.
- Read the current save's `level.dat0` metadata; `level-init.dat` describes creation state. A successful load or an empty prototype-removal report does not prove state preservation: compare relevant properties, inventories, fluids, module capacity, research, paid crafting progress, connections and entity references against the authentic old release where needed.
- Source-backed startup setting transfers must preserve other serialized values. Query native effective setting defaults on disposable verification copies rather than guessing computed defaults from source text. Report unreadable personal blueprint previews as unknown; never modify the player's library to make a test pass.
- For each changed mod, check the relevant API, actual features, placement and save behavior. Include rotation, belt snapping and robot-built rotated/mirrored blueprints when loader code changes. Record the exact tested source and archive identities, including across rebases.
- Distinguish implemented, tested, installed, committed, pushed and published. Never imply that one proves the others.
- Keep current release tables separate from private migration candidates. A settings-only revision may reuse unchanged runtime evidence only through recorded exact control/prototype bytes and native evaluated-domain parity; record the original test identity and the exact engine and artifacts used for graphical or peer checks.
- Performance claims require a named workload, engine/mod versions, measurement units and preserved behavior. Do not generalize a script timing improvement into an FPS/UPS promise.
- Keep a performance optimization only when repeated comparable measurements beat run-to-run noise and behavior checks pass; revert neutral or slower attempts and retain their private evidence.
- Put cheap input, settings-policy and effective-asset checks before long simulations or renderer startup. Explicitly enable or disable every installed builtin from the current save header; omitted builtins can default on. Freeze exact settings exceptions and their source proofs with each profile; do not rely on manually remembered command-line flags. Test affected profiles rather than repeating unchanged suites, and keep proof reuse bound to the exact unchanged runtime files and its stated limits.
- Determine affected saves from each frozen profile's selected mods and hashes. Presence in the combined mod inventory does not establish presence in every save; do not hold unrelated worlds for a shared-inventory failure.
- Publish a new candidate at a new private path, verify it, then atomically change its canonical manifest pointer. Never overwrite an archive before updating its recorded hash. Keep this chat's checkpoint compact and current; archive superseded private records rather than retaining contradictory next steps.
- Public descriptions and release notes describe actual features, fixes and completed tests. Omit labels about unmade or unmeasured improvements, private save names, internal fixtures and conversational naming history. Explain what our fork adds or fixes compared with the original. State support limits where they help players choose or configure the mod.
- Retire a fork only after confirming the original covers its behavior and has no needed custom changes missing. Check complete release histories and explicit maintained continuations without a date cutoff; review actual source and the closest retained-content edition. Distinguish a local replacement in compatible worlds from public retirement when the fork still supports other configurations. Migrate consumers, document the replacement, deprecate the portal entry and archive the related GitHub repository when authorized. Preserve original commit history and verified private backups. Public release/tag cleanup requires explicit authorization.
- Keep one current compatible archive per mod in the active game folder. Back up superseded archives outside it, verify hashes and dependencies, and preserve the player's enablement choices except necessary replacements.
- After publishing, verify GitHub tags/assets, Mod Portal releases, descriptions and the organization catalogue agree. When explicitly authorized, retain one current stable public release/tag per fork and remove the listed obsolete public versions only after verified Git/ref, release-note and asset backups. Preserve original upstream commits and repositories.
- Never lower an already published or installed version to restart numbering or clean history: automatic updates must continue forward under the same mod identity. Preserve published archives by default. An explicitly authorized same-version documentation cleanup requires verified backups and proof that runtime files are unchanged; do not bump runtime versions solely for documentation or history changes.
- Commits for this project use `Co-authored-by: codex <noreply@openai.com>`.
- Update current state, evidence records and asset hashes when facts change; run `python tools/build_database.py` and `python tools/validate.py`.
- Keep `database/documents.json` limited to reviewed public Markdown. Add new shared guides explicitly before rebuilding the index; never index live assignments, private working notes or evidence merely because they are beside the repository.
